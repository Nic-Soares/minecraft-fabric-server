# Versioning

Git stores everything that **describes** the server. Anything that can be downloaded again or that the game generates stays out. The world does not go into Git; it is saved by `backup.sh` in `backups/`.

## What is versioned

| Path | Contents |
|---|---|
| `versions.env` | Pinned versions of the JDK, the game, the loader and the installer |
| `mods.txt` | Intent: Modrinth slugs |
| `mods.lock` | Resolved: exact version, file, sha512 and url of each mod |
| `server/server.properties.base` | Server config, without secrets |
| `server/config/` | Configs generated by the mods (Lithium, C2ME, spark...) |
| `network/tailscale-policy.example.hujson` | Tailscale policy template, without the Mac's IP |
| `scripts/` | `start.sh`, `mods.sh`, `rcon.py`, `backup.sh`, `.env.example` |
| `launchd/minecraft.plist.template` | launchd job template; `service.sh` generates the real plist |
| `.githooks/` | `pre-commit` (secrets and binaries), `commit-msg` (format) |
| `.gitmessage` | Commit message template |
| `README.md`, `CHANGELOG.md`, `docs/` | Documentation and release history |

## What stays out

| Path | Reason |
|---|---|
| `scripts/.env` | Passwords (`RCON_PASS`, `MGMT_SECRET`) |
| `server/server.properties` | Generated on every boot by `start.sh`; the server rewrites the file |
| `server/*.jar`, `server/libraries/`, `server/versions/`, `server/.fabric/` | Recreated by the Fabric Installer from `versions.env` |
| `server/mods/` | Recreated by `mods.sh sync` from `mods.lock` |
| `server/world/`, `server/logs/`, `server/usercache.json` | State and runtime |
| `server/whitelist.json`, `server/ops.json` | Player nicks and UUIDs |
| `network/tailscale-policy.hujson` | Real policy, with the Mac's Tailscale IP |
| `backups/` | Large binaries (`.tar.zst`) |

`.gitignore` ignores all of `server/*` and opens explicit exceptions. A new file created by the server stays out of Git until someone decides it is configuration.

## Pinned versions

```bash
JAVA_VERSION=25
MC_VERSION=26.3
LOADER_VERSION=0.19.5
INSTALLER_VERSION=1.1.2
```

The scripts read only this file. Bumping the game version becomes a small, reviewable diff.

## Mods: intent and lock

The model is the same as `package.json` and `package-lock.json`.

| Command | What it does | Network |
|---|---|---|
| `scripts/mods.sh update` | Resolves the latest build of each slug for `MC_VERSION` and rewrites `mods.lock` | Modrinth API |
| `scripts/mods.sh sync` | Deletes `server/mods/`, downloads what is in the lock and verifies the sha512 | Only the lock URLs |

`mods.lock` format (TSV, sorted by slug):

```
slug	version_id	filename	sha512	url
```

Update flow:

1. `scripts/mods.sh update`
2. `git diff mods.lock` to review what changed
3. `scripts/mods.sh sync` and test the server
4. Commit: `mods: lithium 0.26.1 -> 0.26.2`

Rollback: `git revert <commit>` + `scripts/mods.sh sync`.

## Secrets

- The versioned config is `server/server.properties.base`, without `rcon.password` and without `management-server-secret`.
- `start.sh` merges the base with the values from `scripts/.env` and writes the real `server.properties` before starting the JVM.
- `scripts/.env.example` documents the variables; the real `.env` has permission 600 and is never committed.
- The `.githooks/pre-commit` hook blocks:
  - `.jar`, `.zst`, `.mca`, `.dat` and `.env` files
  - any added line with a value in `rcon.password`, `management-server-secret`, `RCON_PASS` or `MGMT_SECRET`

The hooks are enabled by `git config core.hooksPath .githooks`. This config is local: after cloning on another machine, run the command again.

## Branch flow

| Branch | Role | Branches from | Merges into |
|---|---|---|---|
| `main` | Production: what runs on the server you play on | none | none |
| `development` | Integration and testing | `main` (once, at the start) | `main` |
| `feature/<name>` | One change: new mod, JVM flag, script | `development` | `development` |
| `fix/<name>` | Fix | `development` | `development` |

Lifecycle of a change:

1. `git switch development && git pull`
2. `git switch -c feature/add-distant-horizons`
3. Make the change, test with `scripts/start.sh` and commit
4. Pull request `feature/...` into `development` and merge
5. Test `development` running for real for a while
6. Pull request `development` into `main`, merge and release tag (see [Versions and releases](#versions-and-releases))

Never commit directly to `main`. On GitHub, protect `main` (Settings, Branches, require pull request) and set `development` as the default branch, so PRs open against it by default.

## Commit message

Format:

```
<scope>: one-line summary

Body explaining what changes and why, with the context of the problem.
Lines of up to 72 characters, so git log stays readable even when
indented. Can have several paragraphs.

Reported-by: Name <email>
```

| Rule | Why |
|---|---|
| First line with scope and up to 72 characters, no trailing period | It is what shows up in `git log --oneline`, gitk and shortlog |
| Scopes: `config`, `mods`, `jvm`, `scripts`, `docs`, `git` | Filters history by area: `git log --grep '^mods:'` |
| Written in English | The repository is public; one language for commits, docs, file names and script output |
| Second line blank | Git uses it to separate the title from the body |
| Body lines of up to 72 (the hook tolerates 74) | Readability in the terminal |
| Body explains the why; the diff already shows the what | Context the code does not keep |

Automation:

- `git commit` without `-m` opens the editor with the `.gitmessage` template (enabled by `git config commit.template .gitmessage`).
- The `commit-msg` hook rejects the commit if the format is wrong and says which rule failed. `Merge` and `Revert` commits generated by Git are accepted as they are.
- No sign-off trailers (`Signed-off-by`, `Co-Authored-By`): the author is already recorded in the commit itself.

## Versions and releases

The project follows [SemVer](https://semver.org/): `vMAJOR.MINOR.PATCH`. The version belongs to the **project** (scripts, configs, docs), not the game. The game version stays in `versions.env` and appears in the `CHANGELOG.md` of each release.

### What the public contract is

SemVer needs an "API" to decide what breaks. Here it is everything you or an external script depend on:

- Script commands and arguments (`service.sh start|stop|restart|status`, `mods.sh update|sync`, `backup.sh`)
- `scripts/.env` variables and the format of `versions.env` and `mods.lock`
- Paths that hold state: `server/world/`, `backups/`, `server/whitelist.json`, `server/ops.json`
- World compatibility: a world saved in this version opens in the next one without conversion

### Which number to bump

| Change | Example | Before 1.0 | After 1.0 |
|---|---|---|---|
| Breaks the contract or is irreversible | Bumping the game from 26.3 to 26.4 (the world is converted), renaming a `.env` variable, changing a script argument | MINOR | MAJOR |
| New, compatible capability | New mod, new script, on-demand wake-up proxy | MINOR | MINOR |
| Fix or update with no effect on the contract | Mod patch update, JVM flag, doc fix | PATCH | PATCH |

In the `0.x` series the MAJOR rule becomes MINOR: the `0.x` series signals that the contract still changes. `1.0.0` ships when the contract stabilizes: server on a dedicated machine and an API or web panel that depends on it.

### How to publish a release

1. On `development`, move the contents of `[Unreleased]` in `CHANGELOG.md` to a `[X.Y.Z] - YYYY-MM-DD` section and commit: `docs: prepare release vX.Y.Z`
2. Pull request `development` into `main` and merge
3. Annotated, signed tag on the `main` merge:

   ```bash
   git -C ~/Servers/minecraft switch main && git -C ~/Servers/minecraft pull
   git -C ~/Servers/minecraft tag -s vX.Y.Z -m "vX.Y.Z"
   git -C ~/Servers/minecraft push origin vX.Y.Z
   ```

4. On GitHub: **Releases** tab, **Draft a new release** button, pick the tag and paste the `CHANGELOG.md` section

Tags only on `main`, never on `development` or branch commits. A published tag is never moved or deleted: if the release shipped with a defect, the fix becomes the next PATCH.

### Rollback

`git checkout vX.Y.Z` + `scripts/mods.sh sync` goes back to that release's stack. If the following release bumped the game version, also restore a world backup made before it: Minecraft does not open a converted world in an older version.

### Backups tied to the commit

`backup.sh` puts the short hash in the file name, for example `world-2026-09-27-1530-a1b2c3d.tar.zst`, to know which stack that world ran on. `git describe --tags <hash>` tells which release it belongs to.

## Rebuild the server from scratch

```bash
git clone git@github.com:<user>/<repo>.git ~/Servers/minecraft
cd ~/Servers/minecraft
git config core.hooksPath .githooks
git config commit.template .gitmessage
cp scripts/.env.example scripts/.env && chmod 600 scripts/.env
scripts/install.sh
scripts/mods.sh sync
```

Then just restore a `backups/*.tar.zst` into `server/world/`. `install.sh` reads `versions.env` and runs the Fabric Installer.
